# Domain vocabulary

Shared language for specs, code and reviews. When a term here and a name in code disagree, one of them is wrong.

| Term | Meaning |
| --- | --- |
| **User profile** | The local owner of all data. Single user today; modeled so more profiles can exist later without a login system. |
| **Channel** | A brand: niche, themes, aesthetic, language, target country and a default persona. Owns one or more network accounts. |
| **Network** | A social platform: YouTube, TikTok, Instagram Reels, X, Kick. |
| **Network account** | A channel's profile on one network: credentials (in Windows Credential Manager), metadata defaults and render preset overrides. |
| **App credentials** | The client id and secret of the OAuth app the user registered on a network (Google Cloud OAuth client, TikTok app, Meta app), entered once in Settings and kept in Windows Credential Manager per user profile. Bardo ships none of its own (ADR-0008). |
| **Network connection** | A network account signed in through the network's OAuth with the user's app credentials: its tokens in Windows Credential Manager per network account, and in SQLite only the connected identity, scopes and expiry. YouTube and TikTok sign in through the browser; Instagram, whose login offers desktop apps no loopback redirect, through a user token pasted from Meta's Graph API Explorer, traded for a long-lived one and renewed a week before it expires. When a token reaches several accounts (Pages with a linked Instagram account), the user picks one. *Reconnect needed* when the network refuses a refresh or the connected identity changes; disconnecting revokes the token, except where the network revokes app-wide and another connected account still uses it, or where revoking needs the app credentials (TikTok) and they are gone. |
| **Persona** | A reusable narrator identity owned by the user profile: voice reference, tone, script style and generation presets. Assigned to a channel as default and overridable per video. |
| **Voice reference** | A pointer to a voice held by a voice provider (e.g. an ElevenLabs voice id). The voice itself never lives in Bardo. |
| **Persona package** | A persona exported to a file (`.bardo-persona`, versioned JSON): name, tone, script style, presets, voice reference and the realistic voice flag. Never audio, keys or local ids. Importing adds a new persona to the library; a newer format version than the app reads is refused. |
| **Voice flag** | Marks an imported persona whose voice is not known to be in the user's provider account: *unchecked* until a voice listing looks it up, *unavailable* when the listing lacks it. A flagged persona cannot narrate; a listing that has the voice, or picking a listed voice, clears it. |
| **Voice sample** | A short clip to hear a voice on the Personas screen before narrating with it: the provider's *stock preview* of a voice in the picker (free, but deaf to the presets) or a *reading* of a short sentence (the interface language's, or typed) with the form's voice and presets, saved or not, by the narration model. A reading is a paid call recorded in Costs. Samples are kept on this machine by a key of everything that changes the sound, so hearing the same combination again is free. |
| **Niche** | A content market (e.g. "space history"). Scored for competition and trend. |
| **Market** | A channel's target country plus content language. Market data is fetched and cached per niche and market. |
| **Niche research** | A job that fetches recent uploads for a channel's seed niches (YouTube Data API) and scores each niche. Results are cached with their fetch date for 7 days; refresh fetches again. |
| **Competition** | 0–100 score of how hard a niche is to stand out in: upload volume, channel size and few views per upload push it up. |
| **Trend** | 0–100 score of how fast a niche's recent uploads gather views (median views per day). |
| **Opportunity** | The average of trend and room left by competition (100 − competition). Research results rank by it. |
| **Theme** | A specific video idea inside a niche: a title and an angle. Claude suggests themes, the decision engine ranks them, and the user edits, discards or approves each one. |
| **Interface theme** | How the app itself looks: colors, corner radius, border width and font, never layout. Ten ship: four base themes (Paper, Sand, Graphite, Slate), high contrast light and dark, and four terminal themes (Black Gold, Brass, Phosphor, Phosphor Light) with square corners and a monospace font. Not a **Theme**, which is a video idea. |
| **Theme preference** | A profile's choice of interface theme: follow Windows (a light and a dark theme, switched as Windows switches) or always the same theme. Defaults to following Windows with Paper and Graphite. |
| **Layout** | Where every screen places its parts, chosen per profile in Settings › Appearance: Workspace (a sidebar by pillar, a stepper over the project, cards with the inspector beside them; the default) or Studio (top tabs, compact stage tabs, tables with the inspector in a bottom panel, a status bar). A layout only places things: every screen builds the same parts (header, stages, toolbar, notices, collection, inspector, content, aside, figures, sections) and each layout arranges them, so a new layout is a new variant and arrangement and nothing else. The editor is the same in every layout. Every layout sits under the same title bar, drawn by Bardo in the interface theme (the editor's palette over the editor) in place of the system's caption: the app mark and name, a drag area and the window buttons. Every UI change has to work in every layout; from issue #61 on, each UI slice carries "works in every layout" as an acceptance criterion. Not an **Interface theme**, which colors things and never moves them. |
| **Guided tour** | A walk through Bardo on the user's own data: the content area dims, one component at a time is lit and ringed, and a card beside it says what it is and how to use it (Back, Next, Skip tour, and Learn more when the step has a guide section; ←, →, Enter, Esc, Tab). A tour only explains: clicks outside its card are absorbed, it never changes data, and jobs keep running. Finish leaves the user where the tour ended, Skip tour takes them back to where it started, Esc closes it midway for **Resume tour**. It waits behind the missed posts list. The **welcome tour** is offered the first time Bardo opens on a profile. A **screen tour** explains one screen (Research, Themes, Performance): **Tour this screen** in its header, or Shift+F1, starts it once the screen has something to show, marked *New* from the first visit with content until completed or dismissed (unless *Offer tours on new screens* is off in Settings). Tours never start on their own; they start from the **Guide**, a screen's button or a guide page's Show me. Design in `docs/design/onboarding.md`. |
| **Tour anchor** | The name of a component a guided tour can light: a pillar's group or a place in the navigation, or a part of a screen (header, stages, toolbar, collection, inspector, content), or a screen's own control (a field, a button, a card). The layouts and screens tag what they draw; the tag records where it is in every frame, so the light follows any layout, theme, language or window size. A step whose anchor is not on screen skips, lights the part that holds it, or shows its card in the middle, as the step says. |
| **Tour progress** | Per profile and tour: the content version the user saw, the state (offered, in progress, completed, dismissed), the last step and when it changed. A tour whose content version rose since reads as *New* in the Guide; it never restarts on its own. Reset tours clears it, and the welcome offer comes back. |
| **Guide** | A pinned place beside Jobs, Costs and Settings that opens a menu over the screen: User guide (F1), the welcome tour (marked *New* until started or turned down, and again when its content changes), Tour this screen (Shift+F1) when the screen has one, Resume tour, Keyboard shortcuts and Reset tours. |
| **User guide** | How to use Bardo, written once as Markdown in `docs/guide/<language>/` (en-US and pt-BR, the same pages and sections in both) and read in two places: the **Guide screen** inside the app, which embeds the pages when it is built, and the repository (later a site). Its contents are grouped by pillar: Getting started, Strategy, Production, Editing, Publishing, Costs and budgets, Reference; empty groups are left out. Search ignores accents and case and needs every word. F1 opens the page for the current screen, project stage or Settings tab, else the first page. A tour step can point to a guide section ("Learn more"). Every slice that changes what the user sees updates its guide page and its tour in the same PR. Tests keep both languages in step, every link resolving and every tour step's section existing. |
| **Guide page** | One page of the user guide: an id (its file name), a title, a group, optionally the place it explains (`research`, `projects/script`, `settings/keys`) and the tour that shows it, then sections, each with an id both languages share. The Guide screen shows the contents as the collection, the page as the content and "On this page" as the aside, with the section links, "Show me" (the page's tour) and "Go to" (its place). Links point to another page or section (`page.md#section`), a place (`bardo:go/…`), a tour (`bardo:tour/…`) or the web (opened in the browser). |
| **Theme ranking** | The decision engine's reasons for a theme: fit (with the channel), trend (demand now) and competition (how crowded the angle is), each a 0–100 score with a confidence, plus past performance once the channel has history. Priority weighs fit 40%, trend 35% and room left by competition 25%; past performance takes 5% per published video with a first week (up to 25% from five), the other three sharing the rest in the same proportions. The ranking's confidence is its least certain reason. Editing a theme's text drops its ranking until it is ranked again. |
| **Past performance** | How the channel's own published videos did, as the theme ranking reads it: each video project's **first week** and where it stands against the channel's usual (the median first week: far below, below, about, above, far above). The engine reads the newest 40 and scores how an idea would do next to the ones most like it; the reason shows the average first week of the channel's videos in the theme's niche (or of all its videos, when the niche has none). Fixed when the ranking job starts. Ideas ranked before the channel had history keep their ranking until the user ranks again. A channel with no video that has a first week ranks exactly as before. |
| **First week** | A publication's views seven days after it went live, read off its metrics snapshots: in a straight line between the snapshots around day seven; along a square-root curve from zero when the first snapshot comes in the second week, or projected along it from the newest snapshot of the first week (at least two days old). A publication first synced after its second week, with no earlier snapshot, has no first week. A video project's first week adds up its publications'. It always reads the public views, also when owner metrics are there: they arrive days late, so they would not say the views at day seven, and a channel's older posts or unconnected channels have none to compare with. Instagram and TikTok posts have no public views: their first week reads the views of their **post insights**, which on Instagram run up to 48 hours late. |
| **Narration** | A video project's script read aloud by its persona (the project's own, else the channel's default; ElevenLabs), saved as an MP3 in the project folder with its word timings, the voice and presets used, the model and what the provider billed. Long scripts are read in parts and joined. It belongs to the text it read: once the script changes, the narration is stale until generated again. |
| **Word timings** | When each word of the narration is spoken. Comes with generated narration (the provider times each character; Bardo maps those onto the script's words); computed by alignment for imported audio. Drives the highlighted word in playback, captions and cut snapping. |
| **Project folder** | Where a video project's media lives on disk: `%LOCALAPPDATA%\Bardo\projects\<project id>`. The database keeps file names; the files stay where the user and other tools can reach them. |
| **Template** | A versioned, editable prompt/plan used to generate a script, title, description or media prompt. Its instructions and prompt hold `{{variable}}` placeholders from a fixed set per kind; saving changed text creates the next version and old versions stay readable. |
| **Script** | What the narrator says in a video project. Generated by Claude from the script template, then edited freely by the user. A regenerated script waits for review next to the current one, which stays until the user accepts the new one. |
| **Scene plan** | A video project's narration split into scenes by Claude from the image prompt template. Scenes start on sentences and run back to back from the first word to the end of the narration, so each scene's time comes from the word timings. One plan per project; planning again replaces it (and its images, after the user confirms). It belongs to the narration it was planned on: a new narration makes it stale. |
| **Scene** | A stretch of the narration with one image: its start and end, the narration spoken over it, Claude's image prompt and the user's edited one, its image, a newer image waiting for review, and why its last drawing failed. Drawing a scene again keeps the current image until the user accepts the new one. A scene may also have a clip, with its own motion prompt and video model. |
| **Image generator** | Draws one image from a prompt. Implemented by Nano Banana (Gemini image model), 16:9 at 2K. A request the provider's safety rules decline fails that scene only. |
| **Clip** | A short video a video provider makes from a scene's image (image to video), saved as an MP4 in the project folder with its generation, length and the image it animated. As long as the scene is narrated, within the lengths the model allows. A new clip waits for review like a new image; a scene without a clip keeps its still image. A clip of an image the scene no longer uses is stale. |
| **Motion prompt** | How a scene's image moves in its clip: subject, action, camera. The scene's image prompt unless the user writes one. |
| **Video model** | The provider model that makes clips, e.g. Kling 3.0 through Higgsfield, or Veo 3.1 Fast at 720p through Google. A channel picks the one its scenes use (the provider's default otherwise); any scene can pick another. |
| **Clip generator** | Makes clips asynchronously: hand over the image, submit, poll, download. Implemented by Higgsfield and by Google (Veo and Gemini Omni Flash, on the Gemini key; the image goes inline with the submission). The job saves the provider's request ids before waiting, so a restart polls the same requests instead of paying again. |
| **Generation** | The provenance of a generated asset: provider, model, the final prompt sent, the template version and the tokens used. Never changes; editing the asset leaves its generation as it was. |
| **Video project** | One video in production: script, generated assets, timeline, per-network metadata and publications. Starts when the user approves a theme and stays linked to its channel, niche and theme. |
| **Asset** | Any media file in a project: generated image, video clip, narration, music, SFX or imported file. |
| **Imported media** | Audio or video the user brings into a video project (music, SFX, footage). Bardo reads it with ffmpeg first, refuses what it cannot play, and copies it into the project folder; the user's file is never changed. Audio goes on the music or SFX track, footage on the video track, where its picture plays without its sound. |
| **Music prompt** | The text Claude writes, from the music prompt template, for the user's own music tool. Bardo does not make music: the user edits and copies the prompt, makes the track elsewhere and imports it. Generating again replaces the prompt, edits included. |
| **Timeline** | Ordered clips on video and audio tracks, with cuts, gain, fades and captions. The video track is magnetic (clips run back to back, so removing or reordering one moves the ones after it); audio items sit where they are put, with silence between them. Starts as the rough cut built from the scene plan and narration. |
| **Cut** | The user's edits to a timeline (split, trim, move, reorder, delete), saved as they are made and undoable within the editor session. A cut belongs to the scene plan and narration it was made on: a new plan or narration starts it over from the rough cut. Cuts snap to the narration's word boundaries unless snapping is off. |
| **Cut suggestion** | A point where the decision engine thinks the picture could cut, with a 0–100 score, a confidence and its reasons: a sentence end, a pause of 300 ms or more, a scene change in the script, a topic shift. Candidates are the open points of the cut: those not already cut and at least a second from a cut or a clip's end. The script goes to the engine in stretches that fit its context, the points marked in the text. Suggestions are saved in narration time, so they outlast edits; nothing changes until the user accepts one, which cuts the picture like a manual split (undo takes it back). Rejected ones leave the timeline until the user asks again, and asking again replaces the whole set. Those under the profile's floor (0.50 unless changed) are hidden unless the user shows them. |
| **Mix** | How the timeline's audio tracks (narration, music, SFX) are balanced: each track's level, mute and solo, plus music ducking. Part of the timeline, saved with the cut and undoable; preview and render play the same mix. A soloed track silences every track that is not soloed. Fades belong to each audio item (fade in, fade out), not to the track. |
| **Ducking** | Lowering the music while the narration speaks, by an amount the user picks (12 dB unless changed). Follows the narration's word timings as they sit in the cut: it starts lowering just before a word (150 ms), comes back up after it (500 ms), and stays down across pauses shorter than a second. On unless the user turns it off; muting or soloing the narration does not change it. |
| **Caption** | One line of on-screen text from the narration's words: grouped by length (32 characters), time (3 s) and punctuation. Captions are timed in the narration, so they show wherever the cut plays their words and go with the narration cut away. The user edits a caption's text and ends, deletes one, or turns captions off; each is an edit like any other. Burned into the picture in preview and render. |
| **Caption style** | How captions look: Clean (white with an outline), Boxed (on a dark band) or Punch (large yellow capitals). A channel's style starts each new project's captions; a project can pick another, for all its captions at once. The style is part of the cut, so a cut that starts over takes the channel's style again. |
| **Framing** | The shape of the frame a cut is made for (16:9 or 9:16) and how each clip fills it. Scene pictures are 16:9, so a 16:9 cut shows them whole; in 9:16 each clip either fills the frame with a window of its picture placed across it (centered unless moved) or fits whole with bars. Part of the cut, saved and undoable; a cut that starts over keeps its frame shape. |
| **Proxy** | A low-resolution copy of a clip (540 lines, every frame a keyframe) that preview decodes instead of the original, so playback and scrubbing stay light. Built in the background; the render always reads the originals. |
| **Render preset** | Output format per network (aspect ratio, resolution, codec, bitrate, duration limit, loudness target). Each network has a built-in one; a network account overrides single values, and the rest follow the built-in. |
| **Render** | Producing the final media file from a timeline. Irreversible in cost/time; requires review. |
| **Render review** | What the user sees before a render: the cut's length, frame, mix loudness and captions, and each network account of the channel as a target in its render preset, with its quality gates and last file. Nothing renders until the user confirms the targets they chose; a cut changed after the review is reviewed again. |
| **Quality gate** | One thing the render review flags about the cut or a target, with its reason: over the network's duration limit or no working encoder for the codec (both block that target), a reframed output, captions off, missing media, a silent mix, a mix far from its loudness target, peaks the render will limit (warnings). Measured locally from the cut and ffmpeg, not asked of the decision engine. |
| **Publication** | A render sent (or scheduled) to one network account, with its metadata and status. Requires review. |
| **Uploaded publication** | A publication Bardo sent to the network after the upload review: queued, uploading, processing, then scheduled, published, draft sent (TikTok inbox) or *restricted* (the network kept it private although more was asked, because the user's app is not audited; not a failure); failed keeps its reason (quota, upload limit, reconnect, rejected, processing failed, removed). Its link is the network's address of the video once the whole file arrived. Uploading replaces a manual publication of the same network, and linking a post replaces an upload, each only after the user confirms; neither happens while the upload runs. A TikTok **draft sent** has no link: the creator posts it in the TikTok app, and linking that post replaces the draft without asking again. |
| **Upload review** | What the user confirms before an upload starts: the rendered file of the account's preset, the title, description and tags as the network takes them, the connected channel, the visibility, made for kids and the synthetic-content disclosure (on when the narration uses a realistic voice, editable). Nothing is sent from the review itself; a cut, render, metadata, disclosure or connected channel change after it needs a new review. A Reel's review shows the caption (hashtags in it) and the connected account instead, and asks for the cover frame (seconds or m:ss from the start, within the video), "Also show in Feed" (on unless changed) and the AI label (the disclosure); it has no visibility or made for kids, its publish time is a **due time**, and a file that fails the **Reel specs** blocks it. A TikTok review shows the file, the connected account and the caption to paste (hashtags in it), says plainly that the post is finished in the TikTok app, and asks only whether to be reminded of TikTok's AI-generated content label (the disclosure); it has no visibility, publish time or made for kids (TikTok takes none from apps, and Bardo does not schedule drafts), and a file that fails the **TikTok specs** or an account at its **drafts cap** blocks it. |
| **Reel specs** | What Instagram takes as a Reel, checked on the rendered file before the review opens: MP4 or MOV with its index (`moov`) before the media, H.264 or HEVC, 23 to 60 frames per second, at most 1920 pixels wide, 3 seconds to 15 minutes, at most 300 MB. Each one it fails is listed and blocks the upload, like a quality gate. Bardo's own renders meet them (fast start, constant frame rate). |
| **TikTok specs** | What TikTok takes from apps, checked on the rendered file before the review opens: MP4, WebM or MOV, H.264, H.265, VP8 or VP9, 23 to 60 frames per second, 360 to 4096 pixels per side, at most 10 minutes and 4 GB. Each one it fails is listed and blocks the upload. |
| **Drafts cap** | TikTok keeps at most 5 drafts from apps pending in a creator's inbox in 24 hours, and does not report how many are pending. Bardo counts its own to the same creator, from any account: one for each upload it started (each init) in the last 24 hours, whatever became of it, and one for an upload that waits to start. With 5, the review refuses a sixth and says when the oldest leaves the window. When TikTok still refuses one (drafts from other apps), the upload stays queued like a Reel over its publishing limit, until Bardo's oldest draft leaves the window, or for an hour when Bardo's own do not fill it. |
| **Publishing limit** | How many posts an Instagram account may publish through apps in a moving 24-hour window, read from Instagram (`content_publishing_limit`) each time, never assumed. Read before a Reel's container is made and again before it is published; over the limit, the upload stays queued (holding no place in the queue) and shows when it goes, when the oldest post Bardo published in the window leaves it; when the limit also counts posts made by other apps (which may free a place sooner), it shows when Bardo reads it again, within the hour. A limit the token may not read does not hold the upload, since Instagram enforces it when publishing. |
| **Due time** | When Bardo itself publishes a scheduled post on a network that takes no publish time from apps (Instagram), from the job queue, with the app open and the computer on (the review says so). The upload may start ahead, but no more than 23 hours before, so Instagram still keeps the unpublished container (24 hours) at the due time; the post is published at the due time, not before. The run that publishes it **claims** it first, once, in the same SQLite statement that checks it is due, and the claim stays with the publication: a restart within 15 minutes of the claim resumes that run (Instagram's answer on the container tells whether it already went), and a second runner (the background agent, later) never publishes it again. |
| **Missed post** | A post with a due time that did not go: its time passed while Bardo was closed, Bardo could not start it within 15 minutes of it (the computer slept), or its claimed run was cut short, Bardo opened again more than 15 minutes later and Instagram does not have it published (Bardo asks first). Never sent on its own: its job stops, Bardo lists every missed post when it opens, and the user sends each now, gives it a new time or cancels it (the Publish stage offers the same). |
| **Upload job** | The job that sends a reviewed file with the network's resumable protocol: the network's session is its external handle and the bytes the network confirmed its checkpoint, so stopping, a dropped connection or a restart resumes without sending them again, and an expired session starts over. It then waits for the network to process the video, for about an hour (a quarter of an hour on Instagram); past that the upload shows as still processing and the user checks again. A used-up quota stops it without retrying. On Instagram the session is a resumable container: a resumed upload reads how many bytes the container has and sends the rest; once Instagram has processed it (checked once a minute), the job publishes the Reel, within the **publishing limit**, and keeps what Instagram said it published without (`config_issue`) on the publication. A container Instagram dropped (24 hours unpublished, or gone) makes the job send the file again in a new one, twice at most before it fails. Bardo keeps the Reel's media id on the publication, for its insights. If the account is reconnected as another Instagram account before the upload goes, it fails and the user reviews it again. A render is refused while an upload of its project runs, and a resume while a render runs; an upload resumed after a new render ends, and the user reviews again. On TikTok the upload is a draft to the creator's inbox: the job plans the file in chunks (5 MiB to 64 MB, the last up to 128 MB, `total_chunk_count` = floor(size / chunk)), keeps TikTok's `publish_id` and `upload_url` as its external handle and the last confirmed chunk as its checkpoint; an `upload_url` lasts an hour, so a resume later than that, or one TikTok refuses, starts a new upload. Once the file is in, it checks the status until TikTok puts the draft in the inbox (**draft sent**) or fails it with its reason. |
| **Manual publication** | A publication the user posted by hand from an export, linked to Bardo by its post URL so its metrics can be tracked. One per project and network, and only once that network was exported or a TikTok draft was sent (its render is the one posted). The URL must be the network's own post address (YouTube video or Short, TikTok video, Instagram reel or post, X post, Kick video or clip); short share links are refused because they hide the post id. Linking the same post again keeps its metrics; another post replaces them. A post links to one project. Its posted date is when it was linked until a sync reads the network's own (YouTube's publish time, TikTok's creation time, or the time in the Instagram account's media list). |
| **Video metadata** | One network's post for a video project: title, description and tags. Claude writes every network's at once from the script and each account's defaults (language, default tags, footer), with the metadata template; the user edits them. Each network's limits are domain rules (title and text length with the account's footer and hashtags counted, tag count or tag field length, `<` `>` on YouTube). Text over a limit is kept and flagged, and keeps only that network out of an export. Writing again replaces every network's metadata, edits included, after the user confirms. |
| **Export** | A ready-to-post package for manual posting: `Videos\Bardo\<project title> (<id>)\<network>\` with the network's rendered file, named after its title, and `metadata.txt` (UTF-8, Windows line ends, labels in the interface language) holding each field to paste, the visibility and, when needed, the disclosure reminder. Runs as a job, one network at a time; exporting again replaces that network's files. An export goes out of date when the network's render or post changes. |
| **Synthetic-content disclosure** | The label networks ask for on videos with a realistic synthetic voice or a clone of a real person's voice. A persona carries a "realistic voice" flag (ticked when a cloned or professional voice is picked, editable); when the project's narration was read with a flagged persona, the Publish stage and every metadata file say where each network takes the label. A recording the user imported is never flagged. |
| **Budget** | A monthly spending limit the user sets per AI provider. Reaching it makes new jobs for that provider ask for confirmation. |
| **Provider** | A paid AI or data service Bardo calls with the user's own key: Claude, ElevenLabs, Gemini, Higgsfield, TypeSafe (JEV), YouTube Data API. |
| **Provider key** | The user's API key for one provider, kept in Windows Credential Manager per user profile. Tested with the cheapest authenticated call the provider offers; masked by the redactor wherever text leaves the app (logs, stored errors, screen). |
| **Job** | A long-running task (generation, render, upload, metrics sync) in the queue, with progress, cancel and resume. |
| **Metrics snapshot** | Post-publication statistics for one publication at a point in time. On YouTube: the public views, likes and comments (likes or comments the owner hides stay empty, not zero) and, when the channel's account is connected and YouTube Analytics has data for the post, the **owner metrics**. On Instagram and TikTok: the **post insights** read through the connected account. A number the network did not report stays empty, never zero; a post with no view count yet gets no snapshot. |
| **Owner metrics** | What the channel's owner reads of a post through the connected account, beyond the public statistics. On YouTube (Analytics API, `ids=channel==MINE`): views, engaged views, minutes watched, average view duration and percentage over the post's whole life, and for a channel in the Partner Program estimated revenue, CPM and playback-based CPM; **RPM** is revenue per 1,000 views of the same report, computed by Bardo. A refused money report means **not monetized**: the rest is still read. They arrive 48 to 72 hours late, so a snapshot's owner numbers describe an earlier moment than its public ones; a report with nothing in it yet reads as no owner numbers. **Engaged views** are the headline number when present, for every format: views count every start since 2025-03 (Shorts) and 2026-08 (all formats), engaged views keep the earlier meaning. The **retention curve** (share still watching at each hundredth of the video, and how that compares with videos of similar length) is kept as last read, not per snapshot. An unconnected channel, or one that needs to reconnect, keeps exactly its public statistics. |
| **Post insights** | What the owner reads of an Instagram or TikTok post through the connected account; neither network reports revenue. On Instagram (media insights): views, reach, likes, comments, shares, saves, total interactions and, on a Reel, average and total watch time; data arrive up to 48 hours late and a metric with no data yet is left out (empty, not zero). Insights take the media id: a Reel Bardo published keeps the one it got, and a linked post's shortcode is matched once against the account's media list (newest 2,000) by permalink and the id kept. On TikTok (video query, 20 a call): views, likes, comments and shares; the link already carries the video id. TikTok reports no watch time or retention. Only a post the network shows to its account is returned: one left out (removed, private, not the account's) is flagged like a YouTube post not found. An account not connected, or that needs to reconnect, keeps only the link. |
| **Metrics sync** | A job that reads the public statistics of every YouTube manual publication and every published (not private or restricted) YouTube upload with the user's YouTube Data API key, 50 posts per call (1 quota unit), and stores a snapshot of each post found. A post not found is flagged and keeps its numbers. Runs on "Sync now", after a YouTube post is linked (unless a sync is already running; the next one reads it), and when the app opens if the oldest check is older than the profile's setting (6 hours unless changed; can be off). Instagram and TikTok posts whose account is connected are read through it with no key (see **Post insights**), also on a sync with no key saved; X and Kick keep only the link. For each post it found whose channel's YouTube account is connected, it also reads the owner metrics with the account's token (a report and a retention curve, one Analytics unit each); nothing the owner reads fails the sync (a refused token, quota or connection stops that account's reads for the rest of the sync), and a channel that turns out not to be monetized is read without money for the rest of the sync. |
| **Decision engine** | Answers typed questions (choice, score, yes/no) about a piece of content, with probabilities and confidence. Ranks, scores and gates; never generates content. Implemented by JEV (hosted) and, later, Laya (local). |
| **Text generator** | Writes text (ideas, scripts, prompts) from instructions and a prompt, as prose or JSON in a given schema. Implemented by the Claude API. |
